# 角色走路動畫設計

對應里程碑 M2（見 [ROADMAP.md](ROADMAP.md)）。本文件只定「做法」與驗收方式，**尚未實作**；原型與試驗素材在本機 `private/art-trials/`（不進版控）。四方向素材的產圖結果見 [art/character-briefs.md](art/character-briefs.md)。

## 結論

- 文生圖**不能**可靠地產出多幀走路圖，但**能**產出一致的四個方向站姿（背面、側面實測都和正面是同一個人）。
- 所以走路動畫由程式從「四張站姿母版」變形做出，不另外畫走路幀。
- 做法分三層，逐層疊加，每一層單獨關掉都還能看：
  1. **搖擺步**（四個方向都適用，零額外素材）
  2. **正面與背面抬腳**（把腳切成左右兩塊，輪流抬起）
  3. **側面踏步**（腳整塊不拆，水平伸縮加小幅抬起）
- 已用 2x 母版（128×160）在 canvas 做出原型並逐格檢查：第 1、2 層乾淨；**側面若比照正面把腳切成兩塊，鞋子會被撕裂**（原型實測），所以側面改用第 3 層的做法。

翻轉的代價：不對稱的配件會左右對調（肩背包、手上的平板）。可接受；若日後在意，再為朝右另外產圖。

## 走路循環

遊戲每次按鍵走一格，一格 110 毫秒（`MOVE_DURATION_MS`）。一格就是一步，左右腳交替：

- `step` 為累計步數，奇偶決定「這一步是哪隻腳」。
- `u` 為這一步的進度，0 到 1。
- 一步內：落地 → 離地最高點 → 落地，所以起伏是半個正弦：`bounce = sin(π·u)`，兩端精確為 0。
- **落地姿勢必須等於靜止姿勢**（全部為 0、縮放為 1），走路的開始與結束才不會跳一下。
- 搖擺方向依步數奇偶交替：`side = (step 為偶數 ? +1 : -1)`。

換成原型用的「兩步一循環」寫法：`phase = (step + u) / 2`，`s = sin(2π·phase)`，`bounce = |s|`。

### 參數（初值，來自原型；單位是 2x 母版像素，遊戲內以 0.5 倍顯示）

| 參數 | 值 | 遊戲內約 | 說明 |
| --- | --- | --- | --- |
| `bob` | 4 | 2 px | 上下起伏，落地為 0 |
| `sway` | 3.2° | — | 以腳底中心為軸，左右傾斜，隨步數交替 |
| `airStretch` | 0.045 | 4.5% | 離地最高點 Y 拉長、X 縮小一半（體積大致不變），落地回到原狀 |
| `lift` | 7 | 3.5 px | 正面、背面：被抬腳的上移量 |
| `footStretch` | 0.14 | 14% | 側面：腳部水平伸縮量 |
| `legTop` | 130 | — | 腳的切線（母版 y，裙擺下緣附近）；以下算「腳」 |
| `split` | 正面 60、背面 60、側面 62 | — | 兩隻腳的分界 x（母版）；朝右的值為 `128 − split` |

這些值寫進資料（見下），不寫死在程式；調手感時只改資料。

## 三層做法

### 第 1 層：搖擺步（全部方向）

整張圖以「腳底中心」為軸做 `rotation`、`scaleX/scaleY`、`y` 位移。離地時微微拉長，落地回到原狀（原型曾寫「落地壓扁」，但那會讓落地姿勢與靜止姿勢不同，改為離地拉長）。素材零切割、四個方向一致，是保底層。

### 第 2 層：正面與背面抬腳

- 把母版在 `legTop` 切成上半身與下半身，下半身再在 `split` 切成左右兩塊（兩隻腳之間本來就有縫，切線不會碰到鞋子）。
- 左腳塊在 `sin(2π·phase) > 0` 時向上移 `lift`，右腳塊在 `< 0` 時向上移；**只往上移，不往下**，這樣被抬起的腳會藏到裙子後面，切線不會露出來。
- 繪製順序：先畫兩個腳塊，最後畫上半身蓋住。

### 第 3 層：側面踏步

- 側面兩隻鞋大部分重疊，切成兩塊會撕裂鞋子。改為腳部**整塊**不拆：
  - 以 `split` 為軸水平伸縮 `1 + stretch·s`，一步伸長、一步縮短，模擬前後腳交替；
  - 同時每步抬起 `lift × 0.9 × bounce × 0.5`。
- 原型逐格檢查：沒有撕裂，鞋子略被拉長，遊戲內縮小一半後不明顯。

### 靜止時（idle）

- 回到第 1 層的基準姿勢（全部為 0）。
- 呼吸：`scaleY = 1 ± 1.5%`，週期 2 秒；站定超過 3 秒才開始，之前完全靜止，避免和走路混在一起。
- 眨眼做不到（臉是烤死的），不做。

## 與現有效果的關係

- 取代現有的 `walkBob`（只做上下起伏與位移補間）：位置補間仍由它負責，姿勢（起伏、傾斜、離地拉長、腳）改由新的姿勢函式提供。
- 腳步塵土、轉身壓扁、動作壓扁（`squashSprite`）沿用，並以「基準縮放」為準（M1 已改）。
- 工具揮動與表情氣泡是獨立效果，不在本文件範圍。

## 程式結構

遵守 [TECH_PLAN.md](TECH_PLAN.md) 的分層：規則在 domain、呈現在 presentation。走路姿勢是純呈現的數學，放 presentation，但寫成**不依賴 Phaser 的純函式**，可單元測試：

| 檔案 | 責任 |
| --- | --- |
| `src/presentation/walk-pose.ts`（**已完成**） | `walkPose(step, u, view, params?)` → `{ y, rotation, scaleX, scaleY, legA, legB, stretch }`；另有 `idlePose(stillMs)`、`REST_POSE`、`footModeOf(view)`、`effectiveSplit(view, split, textureWidth)`；純函式。`legA`、`legB` 是腳塊的垂直位移（≤ 0，只往上），`stretch` 是側面腳部的水平伸縮。姿勢數學與 rig 無關，所以不收 rig 參數 |
| `src/presentation/rig-layout.ts`（**已完成**） | `rigLayout(rig, view)`：每個方向的切塊區域與顯示位置（純函式，朝右時從原圖另一端取區域、分界翻到另一側） |
| `src/presentation/character-rig.ts`（**已完成**） | 依 `rigLayout` 把一張貼圖切成上半身與腳的 Phaser 影格（同一張貼圖多個影格），結構為 root（腳底中心，鏡頭跟隨、位置補間）→ body（姿勢）→ 切塊；`setView`、`walkTo`（每次呼叫算一步）、`squash`、`update`（站定後呼吸）、`preview`；載入時核對貼圖大小與 `rigs.json` 宣告一致 |
| `src/infrastructure/assets/rig-manifest.ts`（**已完成**） | `RigDef` 型別與 `rigProblems`（rig 與素材清單的交叉檢查） |
| `content/rigs.json`（**已完成**，目前只有 `player`） | 每個角色素材的 `legTop`、各方向的 `split`（正面、背面、朝左；朝右由程式翻轉）與參數覆寫，以 zod 驗證。腳的做法（`split-legs`／`stretch-feet`）由方向決定（`footModeOf`），不放進資料 |
| `content/assets.json` | `mirrorOf`（已完成）：`player.right` 指向 `player.left`，引擎翻轉，不另存檔 |

切影格用 Phaser 的 `texture.add(name, 0, x, y, w, h)`：**一張貼圖、多個影格**，不產生額外檔案，也不需要預處理工具。

## 測試

先寫測試，再實作（[AGENTS.md](../AGENTS.md)）。

單元（`walk-pose.spec.ts`，純函式）：
- 落地時（`u = 0` 與 `u = 1`）姿勢**完全等於**靜止姿勢，最高點（`u = 0.5`）起伏為 `bob`；相鄰兩步的銜接處沒有跳動。
- 相鄰兩步的搖擺方向相反；兩步一循環後回到原狀。
- 腳塊的 `dy` 永遠 ≤ 0（只往上移，不會露出切線）。
- 左右腳不會同時抬起（正面、背面）。
- 靜止姿勢全為 0。
- 側面不使用切腳模式（`footModeOf` 為 `stretch-feet`，`legB` 永遠為 0）。
- 姿勢中不含 `-0`（`-0` 會讓精確比較出現難查的差異）；進度超出 0 到 1、步數不是整數都會丟 `RangeError`。
- 朝右的分界為 `貼圖寬度 − split`（`effectiveSplit`），且翻兩次回到原值。

內容驗證（`rigs.json`）：每個 `legTop`／`split` 都在貼圖範圍內；`mirrorOf` 指向存在的素材；不得循環。

端對端（Playwright，沿用 `window.__dewhollow`）：
- 靜止時角色外框為 64×80、腳底貼齊格子底部（既有測試）。
- 走一格的過程中，外框頂端的變化不超過 `bob`＋傾斜造成的量（取樣數次），走完後回到靜止位置。
- 四個方向分別使用各自的貼圖；朝右時為朝左貼圖的翻轉（讀 `flipX`）。

視覺驗收（人工，各里程碑一次）：用原型頁面的格狀截圖逐格檢查有無撕裂、切線外露、腳底浮空。

## 視覺驗收的注意事項（M2 第 3 步的發現）

逐格截圖時發現：**無頭 Chromium（Playwright 預設，使用 SwiftShader 軟體繪圖）會把旋轉的切塊畫壞**，上半身被斜切或挖掉一塊矩形，破損位置因相位而異。查證過程：

- 直接讀 WebGL 畫面（`window.__dewhollow.snapshot()`，不經瀏覽器合成）仍然壞，所以不是截圖假象；
- 把 `swayDegrees` 設為 0（不旋轉）後破損完全消失，所以和「旋轉的容器」有關；
- 在 Mac 的實際 GPU（Apple M5 Pro，ANGLE Metal）上，四個方向、12 個相位的輪廓面積與靜止姿勢相比都是 1.00（±0.01），**畫面正確**。

結論與做法：

- 目前判斷是 SwiftShader 的繪製問題，遊戲在實際 GPU 上正常；根本原因（Phaser 4 的繪製方式還是 SwiftShader 本身）**尚未查明**。
- e2e 只驗證姿勢數值與外框，不比對像素，所以不受影響。**像素層級的視覺驗收必須在實際 GPU 上做**（內建瀏覽器或本機有頭瀏覽器），不要用無頭 Chromium 的截圖判斷。
- 開發模式的 `window.__dewhollow.setPose(view, step, u)` 擺出任意相位、`snapshot()` 讀出 WebGL 畫面，供逐格檢查。
- 風險：使用軟體繪圖的玩家（例如某些遠端桌面、虛擬機器）可能看到同樣的破圖。M7 的相容性檢查要確認；若屬實，可偵測軟體繪圖器時把 `swayDegrees` 設為 0 作為保底（已證實關掉旋轉即可避免），或改查 Phaser 的繪製路徑。

## 風險與限制

| 風險 | 影響 | 對策 |
| --- | --- | --- |
| 不是真的走路幀，只是變形 | 近看像「滑步＋搖擺」，不像真的邁步 | 卡通 Q 版、角色小（64×80），多數遊戲採類似做法；若不滿意，再評估人工修兩張走路幀（第二方案）或外包 |
| 一格 110 毫秒，一步很短 | 起伏與抬腳可能快到看不清 | 先沿用，試玩後再決定是否放慢到 140–160 毫秒（只改一個常數） |
| 頭髮、肩背包、平板不會晃動 | 少了次要動態，顯得硬 | 第 1 層的傾斜帶動整體；日後可用 `skew` 或把髮尾切成獨立圖層（P2） |
| 切線在高解析螢幕上露出 | 腳塊與裙子之間出現細縫 | 切線放在裙擺上方 2 px 內（`legTop = 130` 略高於裙擺）；抬腳只往上移，被裙子蓋住。實際 GPU 上逐格檢查未見外露 |
| 軟體繪圖器（SwiftShader）畫壞旋轉的切塊 | 在無頭瀏覽器或使用軟體繪圖的環境，上半身被切掉一塊 | 見上節：視覺驗收用實際 GPU；M7 做相容性檢查，必要時偵測後關掉傾斜 |
| 朝右用翻轉 | 肩背包、平板左右對調 | 已知可接受 |
| 抬腳、搖擺對其他角色（毛毛、寵物）不一定適用 | 每個角色需要各自量出 `legTop` 與 `split` | 資料化（`rigs.json`），新增角色時用同一套工具量測 |
