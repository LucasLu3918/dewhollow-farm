# 角色走路動畫設計

對應里程碑 M2（見 [ROADMAP.md](ROADMAP.md)）。本文件只定「做法」與驗收方式，**尚未實作**；原型與試驗素材在本機 `private/art-trials/`（不進版控）。四方向素材的產圖結果見 [art/character-briefs.md](art/character-briefs.md)。

## 結論

- 文生圖**不能**可靠地產出多幀走路圖，但**能**產出一致的四個方向站姿（背面、側面實測都和正面是同一個人）。
- 所以走路動畫由程式從「四張站姿母版」變形做出，不另外畫走路幀。
- 做法分三層，逐層疊加，每一層單獨關掉都還能看：
  1. **搖擺步**（四個方向都適用，零額外素材）
  2. **正面與背面抬腳**（把腳切成左右兩塊，輪流抬起）
  3. **側面踏步**（腳整塊不拆，水平伸縮加小幅抬起）
- 已用 2x 母版（128×160）在 canvas 做出原型並逐格檢查：第 1、2 層乾淨；**側面若比照正面把腳切成兩塊，鞋子會被撕裂**（原型實測），所以側面改用第 3 層的做法。

## 走路循環

遊戲每次按鍵走一格，一格 110 毫秒（`MOVE_DURATION_MS`）。一格就是一步，左右腳交替：

- `step` 為累計步數，奇偶決定「這一步是哪隻腳」。
- `u` 為這一步的進度，0 到 1。
- 一步內：落地 → 離地最高點 → 落地，所以起伏是半個正弦：`bounce = sin(π·u)`，兩端精確為 0。
- **落地姿勢必須等於靜止姿勢**（全部為 0、縮放為 1），走路的開始與結束才不會跳一下。
- 搖擺方向依步數奇偶交替：`side = (step 為偶數 ? +1 : -1)`。

換成原型用的「兩步一循環」寫法：`phase = (step + u) / 2`，`s = sin(2π·phase)`，`bounce = |s|`。

### 參數（初值，來自原型；單位是 2x 母版像素，遊戲內以 0.5 倍顯示）

| 參數 | 值 | 遊戲內約 | 說明 |
| --- | --- | --- | --- |
| `bob` | 4 | 2 px | 上下起伏，落地為 0 |
| `sway` | 3.2° | — | 以腳底中心為軸，左右傾斜，隨步數交替 |
| `airStretch` | 0.045 | 4.5% | 離地最高點 Y 拉長、X 縮小一半（體積大致不變），落地回到原狀 |
| `lift` | 7 | 3.5 px | 正面、背面：被抬腳的上移量 |
| `footStretch` | 0.14 | 14% | 側面：腳部水平伸縮量 |
| `legTop` | 130 | — | 腳的切線（母版 y，裙擺下緣附近）；以下算「腳」 |
| `split` | 正面 60、背面 60、側面 62 | — | 兩隻腳的分界 x（母版）；朝右的值為 `128 − split` |

這些值寫進資料（見下），不寫死在程式；調手感時只改資料。

## 三層做法

### 第 1 層：搖擺步（全部方向）

整張圖以「腳底中心」為軸做 `rotation`、`scaleX/scaleY`、`y` 位移。離地時微微拉長，落地回到原狀（原型曾寫「落地壓扁」，但那會讓落地姿勢與靜止姿勢不同，改為離地拉長）。素材零切割、四個方向一致，是保底層。

### 第 2 層：正面與背面抬腳

- 把母版在 `legTop` 切成上半身與下半身，下半身再在 `split` 切成左右兩塊（兩隻腳之間本來就有縫，切線不會碰到鞋子）。
- 左腳塊在 `sin(2π·phase) > 0` 時向上移 `lift`，右腳塊在 `< 0` 時向上移；**只往上移，不往下**，這樣被抬起的腳會藏到裙子後面，切線不會露出來。
- 繪製順序：先畫兩個腳塊，最後畫上半身蓋住。

### 第 3 層：側面踏步

- 側面兩隻鞋大部分重疊，切成兩塊會撕裂鞋子。改為腳部**整塊**不拆：
  - 以 `split` 為軸水平伸縮 `1 + stretch·s`，一步伸長、一步縮短，模擬前後腳交替；
  - 同時每步抬起 `lift × 0.9 × bounce × 0.5`。
- 原型逐格檢查：沒有撕裂，鞋子略被拉長，遊戲內縮小一半後不明顯。

### 靜止時（idle）

- 回到第 1 層的基準姿勢（全部為 0）。
- 呼吸：`scaleY = 1 ± 1.5%`，週期 2 秒；站定超過 3 秒才開始，之前完全靜止，避免和走路混在一起。
- 眨眼做不到（臉是烤死的），不做。

## 與現有效果的關係

- 取代現有的 `walkBob`（只做上下起伏與位移補間）：位置補間仍由它負責，姿勢（起伏、傾斜、離地拉長、腳）改由新的姿勢函式提供。
- 腳步塵土、轉身壓扁、動作壓扁（`squashSprite`）沿用，並以「基準縮放」為準（M1 已改）。
- 工具揮動與表情氣泡是獨立效果，不在本文件範圍。

## 程式結構

遵守 [TECH_PLAN.md](TECH_PLAN.md) 的分層：規則在 domain、呈現在 presentation。走路姿勢是純呈現的數學，放 presentation，但寫成**不依賴 Phaser 的純函式**，可單元測試：

| 檔案 | 責任 |
| --- | --- |
| `src/presentation/walk-pose.ts`（**已完成**） | `walkPose(step, u, view, params?)` → `{ y, rotation, scaleX, scaleY, legA, legB, stretch }`；另有 `idlePose(stillMs)`、`REST_POSE`、`footModeOf(view)`、`effectiveSplit(view, split, textureWidth)`；純函式。`legA`、`legB` 是腳塊的垂直位移（≤ 0，只往上），`stretch` 是側面腳部的水平伸縮。姿勢數學與 rig 無關，所以不收 rig 參數 |
| `src/presentation/rig-layout.ts`（**已完成**） | `rigLayout(rig, view)`：每個方向的切塊區域與顯示位置（純函式，朝右時從原圖另一端取區域、分界翻到另一側） |
| `src/presentation/character-rig.ts`（**已完成**） | 依 `rigLayout` 把一張貼圖切成上半身與腳的 Phaser 影格（同一張貼圖多個影格），結構為 root（腳底中心，鏡頭跟隨、位置補間）→ body（姿勢）→ 切塊；`setView`、`walkTo`（每次呼叫算一步）、`squash`、`update`（站定後呼吸）、`preview`；載入時核對貼圖大小與 `rigs.json` 宣告一致 |
| `src/infrastructure/assets/rig-manifest.ts`（**已完成**） | `RigDef` 型別與 `rigProblems`（rig 與素材清單的交叉檢查） |
| `content/rigs.json`（**已完成**，目前只有 `player`） | 每個角色素材的 `legTop`、各方向的 `split`（正面、背面、朝左；朝右由程式翻轉）與參數覆寫，以 zod 驗證。腳的做法（`split-legs`／`stretch-feet`）由方向決定（`footModeOf`），不放進資料 |
| `content/assets.json` | `mirrorOf`（已完成）：`player.right` 指向 `player.left`，引擎翻轉，不另存檔 |

切影格用 Phaser 的 `texture.add(name, 0, x, y, w, h)`：**一張貼圖、多個影格**，不產生額外檔案，也不需要預處理工具。

## 測試

先寫測試，再實作（[AGENTS.md](../AGENTS.md)）。

單元（`walk-pose.spec.ts`，純函式）：
- 落地時（`u = 0` 與 `u = 1`）姿勢**完全等於**靜止姿勢，最高點（`u = 0.5`）起伏為 `bob`；相鄰兩步的銜接處沒有跳動。
- 相鄰兩步的搖擺方向相反；兩步一循環後回到原狀。
- 腳塊的 `dy` 永遠 ≤ 0（只往上移，不會露出切線）。
- 左右腳不會同時抬起（正面、背面）。
- 靜止姿勢全為 0。
- 側面不使用切腳模式（`footModeOf` 為 `stretch-feet`，`legB` 永遠為 0）。
- 姿勢中不含 `-0`（`-0` 會讓精確比較出現難查的差異）；進度超出 0 到 1、步數不是整數都會丟 `RangeError`。
- 朝右的分界為 `貼圖寬度 − split`（`effectiveSplit`），且翻兩次回到原值。

內容驗證（`rigs.json`）：每個 `legTop`／`split` 都在貼圖範圍內；`mirrorOf` 指向存在的素材；不得循環。

端對端（Playwright，沿用 `window.__dewhollow`）：
- 靜止時角色外框為 64×80、腳底貼齊格子底部（既有測試）。
- 走一格的過程中，外框頂端的變化不超過 `bob`＋傾斜造成的量（取樣數次），走完後回到靜止位置。
- 四個方向分別使用各自的貼圖；朝右時為朝左貼圖的翻轉（讀 `flipX`）。

視覺驗收（人工，各里程碑一次）：用原型頁面的格狀截圖逐格檢查有無撕裂、切線外露、腳底浮空。

## 軟體繪圖器會畫壞旋轉的角色（已查明，已加保底）

M2 第 3 步逐格截圖時發現：**無頭 Chromium（Playwright 預設，使用 SwiftShader 軟體繪圖）會把旋轉的切塊畫壞**，上半身被斜切或挖掉一塊矩形。後續查證如下。

### 根本原因

Phaser 4.2.1 的多貼圖著色器（`GetTexture-glsl.js`）用**對內插後 varying 的精確相等比較**來選貼圖：

```glsl
if (outTexDatum == 0.0) return texture2D(uMainSampler[0], texCoord);
else if (outTexDatum == float(INDEX)) return texture2D(uMainSampler[INDEX], texCoord);   // INDEX = 1…7
else return vec4(0.0);                                                                      // 比較全部失敗 → 透明
```

`outTexDatum` 是每個頂點帶的貼圖編號（浮點數），經過光柵化內插後才到片段著色器。GLSL **不保證**內插結果與頂點值逐位元相同：真實 GPU 剛好精確；SwiftShader 內插「軸對齊的方塊」時精確，內插「旋轉的方塊」時有誤差，比較失敗的像素落到最後的 `else`，變成透明。貼圖編號 0 的比較是 `== 0.0`，內插 0 永遠精確，所以不受影響。

這解釋了所有現象：只有旋轉的角色壞（格子是軸對齊的）、只有同一批次有多種貼圖才壞（只有一種貼圖時走 `TEXTURE_COUNT == 1` 的路徑，沒有比較）、搖擺角度為 0 就不壞、破損位置因角度而不規則。

所以答案是**兩者的交集**：Phaser 的著色器依賴了規格沒保證的行為（脆弱），SwiftShader 把它暴露出來；不是單純的 SwiftShader bug，也不是 Phaser 的邏輯錯誤。

### 證據（二分實驗）

| 實驗 | 結果 |
| --- | --- |
| 最小重現：只有 Phaser 加同一張圖（單張、容器、巢狀容器、多影格），Canvas 渲染器當基準 | **不重現**——只有一種貼圖時不壞 |
| 遊戲裡藏起整個地圖（不影響角色） | 破損消失 |
| 只留前 100／300／500／700 個格子 | 仍壞——與數量無關 |
| 所有格子改用同一張貼圖 | 破損消失 |
| 只藏草地格子（仍有其他種類） | 仍壞——與貼圖**種類數**有關 |
| 搖擺角度設為 0 | 破損消失 |
| 攔截著色器原始碼，把精確相等改成 `abs(x - INDEX) < 0.5` | **12 個相位全部 1.00**（決定性實驗） |
| 關掉 `roundPixels`（`pixelArt: false`） | 無影響 |
| 改用 Phaser 官方 API 把每批貼圖數限制為 1 | 12 個相位全部 1.00 |
| 實際 GPU（Apple M5 Pro、ANGLE Metal），四方向 × 12 相位 | 全部 1.00（±0.01），**未破損** |

量測方式：擺出走路循環的各個相位，直接讀 WebGL 畫面（不經瀏覽器合成），量玩家周圍非背景像素的面積，與靜止姿勢相比；破損時掉到 0.67。

### 保底方案與取捨

採用：**偵測到軟體繪圖器時，用 Phaser 的官方 API `renderer.renderNodes.setMaxParallelTextureUnits(1)` 把每批貼圖數限制為 1。**

- 偵測：讀 `WEBGL_debug_renderer_info` 的繪圖器名稱，符合 `swiftshader|llvmpipe|softpipe|software|basic render` 即視為軟體繪圖器（`render-compat.ts`，純函式，有單元測試）。名稱被瀏覽器隱藏時視為硬體；玩家可加 `?compat=1` 強制啟用、`?compat=0` 強制停用。
- 代價（實際 GPU 上量測，目前場景）：**每畫面 draw call 從 1 次變成 90 次**。單一畫面不算多，但會隨地圖複雜度成長，所以**只對軟體繪圖器啟用**，其他玩家完全不受影響。
- 它是通用的：所有旋轉的東西（日後的粒子、旋轉的效果）都受保護，不只角色的傾斜。

評估後不採用的方案：

| 方案 | 不採用的原因 |
| --- | --- |
| 偵測到軟體繪圖器就把 `swayDegrees` 設為 0 | 只保護角色的傾斜，日後其他旋轉的東西仍會壞；且治標不治本 |
| 全面把每批貼圖數限制為 1 | 所有玩家都付每畫面 90 次 draw call 的代價（行動裝置預設本來就是 1） |
| 攔截 `gl.shaderSource` 改寫著色器 | 侵入式，升級 Phaser 時容易默默失效；官方 API 更穩 |
| 把所有素材合成單一圖集（只剩一種貼圖） | 方向正確，M7 的效能預算本來就要做圖集；但角色與地形不太可能全放同一張，**不能依賴**它解決 |
| 只在 e2e 裡避開 | 玩家端仍會壞 |

### 測試與監控

- 單元：`render-compat.spec.ts`（名稱判斷、網址開關、讀取失敗的處理）。
- e2e：`render-compat.spec.ts`
  - 偵測與套用結果一致（`window.__dewhollow.renderCompat()`）；強制開關有作用。
  - **預設路徑像素回歸**：擺出 up／down／left／right 四個方向各 12 個相位，讀 WebGL 畫面量玩家面積；每一項必須在 0.97～1.03，且確認軟體 renderer 預設保底狀態與偵測結果相同。現行測試附上 renderer 名稱、瀏覽器版本與逐相位比值。
  - **強制關閉診斷**：`?compat=0` 只在軟體 renderer 上取樣 down 向 12 個相位，附上目前 renderer／瀏覽器／比值與觀測分類；不以「應當失敗」設成 `test.fail`，因此 renderer 行為變化不會再造成 xpass 假紅。此診斷不會修改預設設定，也不代表停用保底受到支援。
- 歷史紀錄：較早 Chromium／SwiftShader 環境曾以變異測試觀察到停用保底時四個方向的回歸案例失敗；2026-10-26 的完整套件與單獨重跑則在 Google Chrome for Testing `156.0.8078.4`（revision 1248）觀察到 down 向 canary xpass（預期失敗的斷言反而通過）。新版診斷保留當前比值作為證據，不把舊變異結果當成現況。
- **單一 renderer 的 xpass 不足以證明 Phaser／所有軟體或硬體 renderer 都已修復，也不能作為移除保底的依據。** Phaser 升級或 renderer 行為改變時，檢閱附帶的當前診斷；仍維持軟體 renderer 預設保底及 `?compat=1` 強制啟用。移除保底須另做跨 renderer／版本驗證與獨立變更審查。

### 尚未解決與限制

- 瀏覽器隱藏繪圖器名稱（例如部分隱私設定）時偵測不到，需要玩家自己加 `?compat=1`。可考慮之後改成「功能探測」：啟動時用一個小的測試畫面實際繪製旋轉方塊並讀回像素，不靠名稱；目前沒做，因為名稱判斷已涵蓋 Chrome／Edge／Firefox 的軟體退路，先觀察。
- 這是 Phaser 4.2.1 的問題，值得向上游回報（著色器改用容許誤差的比較，例如 `abs(outTexDatum - float(INDEX)) < 0.5`）。我沒有代你發出，需要時請告訴我。
- 強制模式（`?compat=1`）在實際 GPU 上的**畫面**我沒能目視確認（內建瀏覽器窗格隱藏時動畫不會前進）；啟用路徑由 e2e 與控制台訊息驗證，且已知關掉並行貼圖後畫面正確（headless 像素回歸通過）。

像素層級的視覺驗收仍應在實際 GPU 上做。開發模式的 `window.__dewhollow.setPose(view, step, u)` 擺出任意相位、`snapshot()` 讀出 WebGL 畫面、`renderCompat()` 讀出偵測結果，供逐格檢查。

## 毛毛與寵物（M2 第 5 步，已完成）

同一套 rig 擴充為三種類型（`rigs.json` 的 `kind`）：

| kind | 用在 | 圖片 | 動作 |
| --- | --- | --- | --- |
| `biped` | 玩家 | 四方向，上半身與腳切開 | 搖擺步＋正面背面輪流抬腳、側面腳整塊伸縮 |
| `single` | 毛毛 | 一張圖，不切 | 搖擺步（`bodyPose`）：起伏、傾斜、離地拉長，腳的欄位全為 0 |
| `hop` | 黑貓、有袋動物 | 一張圖，不切 | 小跳步（`hopPose`）：跳起一下再落地，不傾斜、不分左右步 |

- `hopPose` 的跳躍高度（`hopHeight`，預設 12）比人走路的起伏（`bob`，4）高，才看得出是跳；兩個姿勢落地時都精確等於靜止姿勢。
- 毛毛目前站著不動，所以搖擺步用在「被搭話時原地搖一下」；日後他有行程（走動）時，直接用同一個 `walkTo`。
- **夥伴（`content/companions.json`）**：`follows: 'player'` 的跟著玩家；有 `home` 的住在某張地圖某一格，`reactsTo` 指定一位居民，玩家跟他說話時夥伴也會跳一下。兩者擇一，有交叉檢查（rig 存在且是 `hop`、home 的地圖存在且可站、不與居民或其他夥伴重疊、reactsTo 的居民存在）。
- **黑貓**：跟著玩家，永遠站在玩家**剛離開的那一格**（`nextPetTile`）；玩家原地轉身牠不動；玩家走到牠的格子上時兩者自然換位。換地圖時（或剛讀檔）站到玩家後面，後面不行就順時針旁邊、逆時針旁邊、最後前面（`placeBeside`，牆、門、居民、玩家本身與被占用的格子都不能站）。
- **有袋動物**：住在村莊毛毛旁邊 (11,5)，離開村莊就不在畫面上。
- 寵物只存在於畫面上，**不擋路、不進存檔**，邏輯在 presentation（純函式 `pet-follow.ts`，有單元測試）。
- 玩家跟居民說話時，應用層發出新的 `talked` 事件（含居民 id；領不到禮物時也會發），畫面據此讓居民與他的夥伴反應。
- 圖層深度：居民 5、跟隨的寵物 9（在玩家後面）、玩家 10。
- 開發模式新增 `window.__dewhollow.actors()`（所有看得見的角色：站的格子、外框、姿勢）與 `setOthersHidden()`（像素量測時藏起其他角色）。

**已知限制**：寵物與毛毛都只有正面圖，所以朝任何方向走都是同一張臉；左右走動時不會轉頭。貓的圖是坐姿，跳著走看起來像「彈跳」，不是邁步；若不滿意，之後再補側面圖。

## 工具揮動與表情氣泡（M2，已完成）

分類與理由見 [ART_PIPELINE.md](ART_PIPELINE.md) 第 5 節：只有 3 件東西產圖（鋤頭、水壺、種子袋，見 [art/tool-briefs.md](art/tool-briefs.md)），其餘是粒子與程式繪製。

**工具揮動**
- 角色圖的手臂是畫死的，所以「手部動作」＝工具圖繞握把旋轉（`toolPose`）＋身體朝目標前傾與輕微壓縮（`actionLean`）＋命中那一刻的粒子。兩個都是純函式（`tool-swing.ts`），朝左是朝右的精確鏡像。
- 資料：`content/tools.json`（工具、動作、素材、握把位置、揮動方式 `chop`／`pour`／`sow`）與 `rigs.json` 玩家的 `hands`（正面、背面、朝左的握工具位置；朝右由朝左翻過來）。都有交叉檢查。新增工具（斧、鎬、釣竿）只加資料與產圖，不改程式。
- 命中的那一刻（`impactAt`）才出現粒子與鏡頭微震（開墾），也才更新被作用那一格的外觀（田地翻土、澆水變深、長出小芽）：遊戲狀態是立刻改變的，但畫面上工具還在空中時，那一格維持動作前的樣子（`heldPlots`）。
- 走路中按下動作鍵（玩家常常「走到就按」）會排隊，走完那一步再揮；被新的動作打斷時，還沒到的命中效果立刻補播，不會丟掉。
- 從正面看工具朝觀看者砸來（變大），從背面看是離開（變小，且畫在身體後面）；兩者幅度約為側面的 60%。
- 「減少動態」（`prefers-reduced-motion`）：揮動幅度降為 40%、不震動鏡頭，工具仍然會出現。

**表情氣泡**
- 六種：愛心、驚嘆、問號、汗滴、音符、睡眠 Z。啟動時用 Graphics 畫成 56×56 的 2x 貼圖（`emote.ts`），顏色全取自共用調色盤（`emote-defs.ts`，有測試）；彈出時由小彈大（最大 1.25 倍）再回到 1，停一下，往上飄並淡出；「減少動態」時只淡入淡出。每個角色最多一個。
- 對應（純函式 `emotesForEvent`，有測試）：玩家領到禮物 → 居民愛心；第一次見面禮物放不下 → 驚嘆；之後搭話 → 音符；體力不足 → 汗滴；背包滿 → 驚嘆；其他被拒絕（沒東西可互動、還沒開墾…）→ 問號；睡覺 → Z；收成 → 音符。
- 應用層新增 `refused` 事件（被拒絕的動作，帶失敗代碼；狀態與時間不變），`talked` 事件加上 `first` 與 `gifted`。

**限制**
- 工具圖只有一張，沒有殘影；手是角色圖裡畫死的，工具疊在她手上的平板前面。
- 朝左用鏡像，水壺朝左時壺嘴朝左。
- 目前只有玩家有 `hands`；毛毛與寵物不揮工具。
- 氣泡是程式畫的，沒有手繪質感；若上線前覺得單調，可以只替換這幾個符號為產圖，資料結構不變。
- 氣泡掛在角色底下，深度與角色相同：黑貓站在玩家上一格時，玩家的氣泡會畫在貓的前面並與牠重疊（仍然看得清楚）。若覺得擠，可以改成讓氣泡永遠畫在最上層。

## 拾取、地形腳步與音效（M2 收尾）

M2 的完成條件是「每個玩家動作都有對應視覺與音效回饋」。這一節補齊最後三項。

**拾取飛行（收成）**
- 作物拱著飛到玩家頭上，縮小、淡出，到頭上後飄出「+名稱」。軌跡是純函式 `pickup-arc.ts`（直線加拱起，尾端縮為 0.55 倍），有單元測試。
- 作物圖用既有的成熟作物圖，不另外產圖。終點每一幀重新計算，玩家飛行途中走開，作物會跟著去找他。
- 出貨的飛行（物品飛進箱子）仍留到 M4，因為需要箱子的正式素材與背包介面。

**地形腳步**
- 離開一格時，腳步塵土的顏色與音效由「那一格的地面」決定。規則與數值在 `content/terrain.json`：草地（淡綠、輕沙沙）、田地（褐色土塊、悶響）、石板路（米色、清脆）。
- 載入時檢查：每種可走的地形都必須有一筆，且指向存在的音效。M3 加入水邊與雪地時只需新增資料。

**音效（程式合成）**
- 配方在 `content/sounds.json`：每個音效是幾條音軌（波形 sine、triangle、square、sawtooth、noise；音高可從 `from` 滑到 `to`；`attack` 與 `duration` 決定音量包絡）。
- `synth.ts` 把配方算成取樣值（純函式，同一份配方結果完全相同，雜訊的種子固定）；`sound-player.ts` 第一次播放時算好緩衝區、之後重用。
- 沒有音訊裝置或瀏覽器拒絕時靜默略過。靜音（按 M）記在本機 localStorage，讀寫失敗就當作沒有記住。
- 對應：點選工具或種子 → `click`；揮動開始 → `swing`；命中 → `till`／`water`／`plant`（收成為 `harvest`、出貨為 `ship`）；睡覺 → `sleep`；搭話 → `talk`；送禮 → `gift`；被拒絕 → `refuse`；存檔 → `save`；腳步依地形。
- 音樂不在本節範圍（M3 起）。

**測試**
- 單元：`synth.spec.ts`（音高滑動的幾何平均、包絡、靜音時段、固定雜訊、音量上限）、`pickup-arc.spec.ts`、`sound-catalog.spec.ts`（程式用到的每個音效都存在、每個音效都能合成且在 1 秒內、音量在範圍內）、`load-content.spec.ts`（地形缺漏、音效不存在、錯誤格式）。
- e2e：`feedback.spec.ts`（依地面順序出現的腳步、收成的拾取紀錄與訊息、揮動的音效在命中前、M 靜音）。
- 開發模式新增 `window.__dewhollow.soundLog()` 與 `muted()`。

**限制**
- 音效的音色只能由人耳判斷；自動測試只能確認「該播的播了、順序對、靜音有效」。請在實機上聽一次，音量與音色若不滿意，改 `content/sounds.json` 即可。
- 腳步目前不分左右腳；每一步的聲音相同。
